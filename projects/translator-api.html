Translator API: the product that became a capability

The plan-era answer to the Docker line: a local multilingual translation service. Its architecture stayed on record after the same requirement was delivered differently, as a general agent capability.

What it was proposed to be

The product spec

A LAN-reachable webapp: single- or multi-speaker, multi-language speech or text input converted into one to four output languages as text, with live correction in the UI. Everything local: model, inference, app. No cloud APIs.

Engine choice driven by the workload

The design spec (approved 2026-09-30) chose vLLM over simpler local runners because the product fires up to four concurrent translation requests per phrase with strict structured output; continuous batching plus native structured-output backends (XGrammar/Outlines) win that workload.

Two-service compose topology

A vllm service (CPU image by default, model mounted read-only, internal to the compose network only) and a webapp service (FastAPI, host port 8000 on the LAN, health-checked containers, restart: unless-stopped). A small .env contract (VLLM_MODEL, VLLM_PORT, WEBAPP_PORT) parameterised the whole stack.

A portability constraint written into the design

AMD GPU passthrough is unavailable on Windows Docker Desktop (WSL2), so the stack defaulted to CPU execution with documented, commented-out passthrough blocks for NVIDIA and AMD RDNA4 (Linux host).

Model strategy

Qwen3.5-4B as the reference family: GGUF reference weights kept for evaluation, with a vLLM-compatible quantisation dropped into the mounted models/ directory at deployment. The vLLM service starts only once a model exists in the mounted models/ directory; the README documents that precondition.

What actually got built (approved scope)

The approved scope line: workspace + full Docker skeleton

Repo with README, compose stack, Dockerfile, env contract, git conventions, design spec and the route-analysis conversation history preserved in docs/. The product features (audio input, live correction, concurrent multi-language UI) were planned in later phases and are labelled as such in the spec.

An endpoint that says 501

The shipped FastAPI app exposes /api/health (it probes the inference service's model list and reports reachability) and a /api/translate that returns 501 not implemented. Tests cover the shipped surface.

Why it was retired: the requirement, delivered as capability

The Goal 4 build superseded it first

While the plan's capstone was being built, the same core requirement (multilingual speech in, text out, locally) was delivered by the CPU audio toolkits: whisper.cpp built for this CPU (Zen 4 SIMD kernels) translating any language to English in one pass at real-time factor 0.065, plus sherpa-onnx diarization separating speakers at 0.04 RTF. The core capability already ran at measured speed without containers.

The requirement became a callable capability

The translator would have been one webapp serving one job over one port. The replacement exposes the same capability through MCP tool doors that any project or agent can call: it is already consumed as live audio transcript notes on the Discord bot (PF12) and as diarized speech notes in video grounding on the Strata stack (PF2).

The retirement stays on the record

The plan's Docker commitment was attempted; when a different goal produced the same capability, the pivot was documented. PF10 stays in the inventory as a retired item, with the replacement and its measured numbers named.
